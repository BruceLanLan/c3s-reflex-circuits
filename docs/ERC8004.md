# Publishing a boundary through ERC-8004, and checking one

[ERC-8004](https://eips.ethereum.org/EIPS/eip-8004) (Trustless Agents, a draft) gives an
agent an ERC-721 identity whose `agentURI` resolves to a registration file, key/value
metadata on chain, and a Validation Registry where a validator answers a request with a
score from 0 to 100. Every off-chain document is committed to by its keccak256.

This repository adds one document to that picture — a **boundary manifest** for one
compiled policy — and a validator anyone can run against it. The maintainers deploy
nothing, register nothing and sign nothing: both scripts *print* `cast send` commands with
`$YOUR_RPC` / `$YOUR_KEY` placeholders for you to run on your own machine, and never read
a key.

## What gets published

`scripts/boundary_manifest.py --policy '{"min_gap_ticks":8,...}' --out manifest.json`
compiles the policy, checks it and writes `c3s.boundary/1` JSON (`c3s/erc8004.py`):

| field | what it holds |
| --- | --- |
| `rules` | the rules in the policy's own words (`describe()`) and the exact settings |
| `inputs` | each input bit in order, with the channel it must come from: `agent` for `request`/`intent`, `tool_layer` for everything else |
| `circuit` | NAND and latch counts, the netlist bytes (`netlist_hex`) and their SHA-256 |
| `checked` | rows checked against the Python reference, domain bits, reachable states, configurations visited, whether every rule holds, violations per rule |
| `lineage` | `parent` = the fly escape core's netlist SHA-256, `parent_name` = `core-hand-abc`, `relation` = `compiled-by-the-same-method` |
| `limits` | what none of the above shows (below) |
| `tool` | package version and git commit that produced it (informational; not validated) |
| `onchain` | only with `--module`: chain id, the `ReflexModule` address, its optional-input mask, the Safe |

The file is canonical — sorted keys, no whitespace, UTF-8 — and its keccak256 is the
`requestHash` (the spec defines that hash as keccak256 of the request payload). Publish the
bytes unchanged; a pretty-printed copy hashes differently and fails the `canonical_bytes`
check. keccak256 is computed with Foundry's `cast keccak`, since the project environment
has no keccak library.

The script also prints a registration file with a `c3s-boundary` entry in `services`
(endpoint = manifest URI, plus its keccak256) and the commands for `register(string)`,
`setMetadata(agentId, "c3s.boundary", {keccak256, uri})`, `setAgentURI` and
`validationRequest`. The boundary is a service and a metadata key, not a `supportedTrust`
value: the spec lists `reputation`, `crypto-economic` and `tee-attestation` and says
nothing about others, while services are explicitly open-ended.

## Who can validate, and how

```sh
python scripts/validate_boundary.py https://example.org/manifest.json --request-hash 0x… \
    --rpc https://bsc-rpc.publicnode.com --rows 8 --out report.json
```

From the manifest bytes alone it recompiles the policy from `rules.settings`, requires the
rules, channels and netlist to equal the recompile, decodes the *published* netlist,
re-runs `verify()` and `properties()` on it and compares every recorded number. With an
RPC it also evaluates a handful of reachable rows of that netlist on a real node through
the same zero-deployment `eth_call` state override `scripts/verify_onchain.py` uses, and,
if the manifest names a module, reads its `netlistSha256()`, `netlist()`, `nIn()`,
`nState()`, `optionalInputs()` and `safe()`. A manifest that names a module cannot score
100 offline. Every check is listed by name with what was expected and what was found.

The `lineage` check is one of them. A compiled boundary is descended from the fly escape
core by method rather than by data — the same compiler, the same whole-domain check, the
same proofs over every reachable state — so a manifest names that core's netlist digest
as its parent, and a manifest claiming a parent that is not the committed core fails,
naming `lineage`. The digest is the parent's name: a copy of the core whose digest
differs is not the circuit this lineage descends from.

Anyone can run it and get the report. Recording the result is narrower: the spec requires
`validationResponse` to come from the validator address the agent's owner named in
`validationRequest`, so an unnamed validator can publish a report but not put a response
on chain for that request. The printed command sends
`validationResponse(requestHash, score, responseURI, keccak256(report), "c3s-boundary")`.

## What a score of 100 means

The score is binary: 100 if every check passed, otherwise 0. **100 means** the published
netlist is exactly what these rules compile to, it equals the Python reference on every
row of its domain, every rule holds in every reachable state, every number in the manifest
is what the checks produce, and (when checked) a public node evaluates the same rows the
same way and the named module holds the same netlist and input layout.

**100 does not mean:**

* that the agent routes every action through this circuit. A local gate bounds only the
  channels that pass through it; only the Safe-module form (the agent is not an owner and
  can act only through `act()`) makes bypassing it structural, and even then the Safe
  owners and the supervisor key sit outside it;
* that the tool-layer flags are honest. `blocked`, `confirm`, `irreversible`, `failed`,
  `heartbeat` and `confirm_b` are promises by whoever writes them;
* anything about time. Ticks are calls or decisions, not seconds or blocks;
* that the module's own code outside the circuit (confirmation keys, selector list,
  block-number windows) is correct — see [ONCHAIN-SELF-DEPLOY.md](ONCHAIN-SELF-DEPLOY.md).

These limits are in every manifest, and the validator fails one that drops them.
