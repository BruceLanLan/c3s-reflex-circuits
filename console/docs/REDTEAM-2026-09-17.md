# Red-team pass — 2026-09-17

Adversary in the model's position: a capable agent on this machine with a shell (and, for
the LAN findings, a passive listener on the same Wi-Fi the pairing flow puts the console
on). Goal: get a grant it should not have, write a person's bit, or keep going after a
person said stop. Everything below was run against a private console (`CONSOLE_PORT=8774`,
and a second one bound to `0.0.0.0` on `8775` for the LAN path), not the user's `8765`.

The two holes the earlier reviews found (`/api/to''ol`, the spoofable unbound name) are not
re-reported. These are the next ones. **Confirmed** means a command and its real output;
**plausible** means reasoned from the code but not executed end-to-end here.

Short version: the boundary's own logic held under every attack I ran — no confirm was
written, no grant was forged, the device could not out-reach the cable, and no non-operator
path lifted a halt. What did break is the **secret-handling around the new LAN posture**:
the operator token, which the whole model calls "the one thing the person has and the agent
does not," is now put on the Wi-Fi in cleartext on every poll — and the design decision the
user asked about (rename past the stop button) is real and worth closing.

---

## Findings, ranked

### F1 — CONFIRMED, high (LAN posture). The operator token rides the Wi-Fi in cleartext, continuously — not "once"

Tonight's change made `GET /api/state` and `/api/manifest` require a token over the LAN, and
the page (`static/index.html` `refresh()`, line 1696) attaches `x-reflex-token: <operator
token>` to **every** `/api/state` poll — `setInterval(refresh, 2000)`, so every 2 seconds,
for as long as the tab is open. There is no TLS (`SECURITY.md` limitation 8). So on the
shared Wi-Fi the pairing QR exists for, a passive eavesdropper captures the operator token
off the very first poll and then holds the person's only secret: it installs rules, writes
`confirm`/`confirm_b`/`blocked`, and presses stop/resume.

The pairing docs say the opposite. `c3s_cli/cli.py:136` and `:139` tell the person "It still
crossed the local network once" / "it crossed this Wi-Fi once", and `_pairing_url`'s
docstring reasons that the fragment keeps the token out of logs and `Referer` (true, for the
*initial delivery*). The fragment delivery is sound. The retransmission is the hole, and the
caveat that says "once" is now false.

Proof the LAN read demands the token (so the page must send it), against the `0.0.0.0`
console on `8775` from this machine's own LAN address `192.168.1.23`:

```
$ curl -s --noproxy '*' -w '\nHTTP=%{http_code}\n' http://192.168.1.23:8775/api/state
{"error": "reading the console over the network needs a token: the operator token
 (X-Reflex-Token — the pairing link carries it) or a bound agent's own token. On this
 machine it needs none."}
HTTP=403

$ curl -s --noproxy '*' -o /dev/null -w 'HTTP=%{http_code}\n' \
    -H 'X-Reflex-Token: rt-operator-token' http://192.168.1.23:8775/api/state
HTTP=200
```

And the page attaches it unconditionally whenever it holds one (`static/index.html:1696`):

```js
const r = await fetch("/api/state", { cache: "no-store", headers: TOKEN ? { "x-reflex-token": TOKEN } : {} });
```

Once captured, the token is full authority — same console, operator token writes a person's bit:

```
$ curl -s -H 'content-type: application/json' \
    -d '{"agent":"agent-old","confirm":1,"token":"rt-operator-token"}' \
    http://127.0.0.1:8774/api/tool -w '\nHTTP=%{http_code}\n'
{"at": ..., "kind": "tool", "agent": "agent-old", "armed": {..., "confirm": 1, ...}}
HTTP=200
```

Two aggravating details:

* The token is stored in the phone's `localStorage` (`reflex.token`) with **no expiry and no
  session scope** — it lives in that browser until someone clears it. `c3s token rotate`
  invalidates the server side, but the phone keeps sending the stale one and a re-pair is
  needed; meanwhile anyone who reads that browser's storage (a later holder of the phone,
  a backup) has the token as it was at capture.
* This is *not* the documented same-uid limitation (limitation 2). That one is about an
  agent on the console's own machine. This is a **network** exposure of the operator token,
  which the threat model's "shared network" section is supposed to be closing, not opening.

**Severity.** High in the `--lan` posture the QR requires; nil on a loopback-only console
(the token still goes in the header but never leaves the host). It needs a listener on the
Wi-Fi, so it is not the same-machine agent the model centres on — but the pairing feature is
exactly what invites strangers onto the path, and the caveat tells the person they are safe.

**Fix (files I do not own — land as you see fit).**
1. Correct the caveat so it is not false. `c3s_cli/cli.py`:
   ```diff
   @@ def _pairing_caveats
   -    if with_token:
   -        say("  The phone keeps the token in its browser; it crossed this Wi-Fi once. "
   -            "`c3s token rotate` replaces it; `c3s pair --no-token` keeps it off the network.")
   +    if with_token:
   +        say("  The phone keeps the token in its browser AND re-sends it on every /api/state "
   +            "poll (there is no TLS), so it is on this Wi-Fi continuously, not once. Pair only "
   +            "on a network you trust; `c3s pair --no-token` keeps it off the network entirely, "
   +            "and `c3s token rotate` replaces it if it may have been seen.")
   ```
   and drop the "cannot appear in a `Referer`"→"once" implication from `_pairing_url`'s
   docstring.
2. The real fix is to stop putting the operator token on the wire for reads. Give the
   paired phone its **own read token** (the device-token machinery already exists for the
   Cardputer — `device_auth` / `X-Reflex-Device-Token`), scoped to `GET /api/state` +
   `/api/manifest`, and let `refresh()` send *that* over the LAN, never the operator token.
   The operator token then crosses the network only on the rare write, and rotating the
   phone's read token does not touch it. This is the structural change; it belongs to
   whoever owns W1/W5 + `static/index.html`.
3. Failing that, ship TLS for the LAN bind (self-signed, pinned in the QR) so the header is
   not in cleartext — heavier, and the phone-trust problem in localStorage remains.

### F2 — CONFIRMED, medium. A bound agent's own token reads the *entire* console over the LAN

`_reader_may_look` (`console.py:1688`) grants `GET /api/state` over the network to
`bound_token_owner(self._agent_token())` — i.e. **any** bound agent's token. But
`/api/state` is the whole console: every other agent's pending `reason`, the 60-entry
transcript, every agent's armed bits and counters. An agent token was introduced (I-3) so a
name could *authenticate its own requests*; it is now also a full-console **read** credential
on the LAN. `docs/ISOLATION.md` leans on the opposite — "a contained agent cannot [read a
pending reason]: the gateway does not carry `/api/state`" — to argue the container cannot
learn the `reason` string it would need to spend someone else's confirm. That holds for the
gateway path, but the console's own LAN rule now hands `/api/state` to any bound agent that
reaches it by a real network address.

Proof — bind `reader` from loopback, have `treasury-bot` leave a sensitive reason, then read
it all back over the LAN with *reader's* token (not the operator's):

```
$ curl ... -H 'X-Reflex-Agent-Token: reader-secret-token' \
    -d '{"agent":"reader",...,"reason":"[exec] reader boot"}' http://127.0.0.1:8775/api/request   # bind, HTTP 200
$ curl ... -d '{"agent":"treasury-bot",...,"reason":"[exec] wire 50000 USDC to 0xBEEF"}' \
    http://127.0.0.1:8775/api/request                                                             # HTTP 200
$ curl -s --noproxy '*' -H 'X-Reflex-Agent-Token: reader-secret-token' \
    http://192.168.1.23:8775/api/state | python3 -c "..."
HTTP ok, agents seen: ['reader', 'treasury-bot']
other agents' reasons in transcript: ['[exec] wire 50000 USDC to 0xBEEF']
```

**What it lets an attacker do.** Turn one agent's token (which the same-uid limitation
already says is readable on the host, and which now also travels the LAN) into read of every
other agent's pending confirms — the exact `reason` strings that limitation 4 / the "what the
container can still do" section say are the missing piece for spending a confirm left for an
unbound name.

**Fix.** When the reader authenticated as an *agent* (not the operator, not loopback), return
a narrowed status: that agent's own rows and the class policies (which are not secret), and
omit other agents' `reason`/transcript/effect. Sketch, in `console.py`:
```
if reader_is_bound_agent_over_lan:
    return {k: v for k, v in status().items() if k not in ("transcript",)} with
           agents filtered to [the caller's own name] and pending filtered likewise
```
Owner of `console.py`'s call; the shape is I-2's.

### F3 — CONFIRMED, low (defence-in-depth only). The hook's self-guard is keyed to `:8765` and to literal host spellings

`adapters/claude_code_hook.py:reaches_the_guard` is the pattern check that refuses an agent's
tool call before it can reach the console. It is documented as *not* the defence (the token
is), so this is severity-low — but it is weaker than a reader of that file would think:

```
$ REFLEX_CONSOLE=http://127.0.0.1:8774 python -c "... reaches_the_guard ..."
BLOCKED :: pkill -f console.py
BLOCKED :: kill $(lsof -ti :8774)
ALLOWED  :: pkill -f 8774
ALLOWED  :: kill $(fuser -n tcp 8774 2>/dev/null)
ALLOWED  :: curl http://127.1:8774/api/tool -d '{"confirm":1}'
ALLOWED  :: curl http://2130706433:8774/api/tool -d x
```

Two gaps: the process-kill clause hardcodes `":8765"` (line 197) instead of the configured
port, so a console on any other port is killable via `pkill -f <port>` or `fuser`; and
`_console_markers()` lists only literal spellings (`127.0.0.1`, `localhost`, `0.0.0.0`,
`::1`), so IP aliases (`127.1`, decimal `2130706433`, `[::ffff:127.0.0.1]`) walk past the
net-tool clause.

The token backstop holds through the bypass, which is why this is low — reaching `/api/tool`
via the alias still cannot write a person's bit:

```
$ curl -s -d '{"agent":"agent-NEW","confirm":1}' http://127.1:8774/api/tool -w '\nHTTP=%{http_code}\n'
{"error": "confirm are the person's: send the token ... An agent may not write these."}
HTTP=403
```

The only thing that goes through the alias is the agent's own `irreversible` bit (HTTP 200),
which is DoS-only and stricter (limitation 3). And killing the console makes the hook fail
**closed** (deny all) unless `REFLEX_FAIL_OPEN=1`, so it is self-DoS, not escalation.

**Fix.** In `adapters/claude_code_hook.py`: derive the kill-clause port from `CONSOLE`
instead of the literal `:8765`, and normalise host spellings in `_console_markers()` (add
`127.1`, the 32-bit decimal, and `::ffff:` forms, or resolve to a canonical address). It
only turns more cheap tries into an early no; the docstring already says so.

## The design question the user has to decide: rename past the stop button

**Confirmed the gap.** The big red button (`stop_all`) writes `blocked` for
`sorted(self.agents)` — the names known at press time. A name first seen afterwards is not
blocked, and an optimiser that renames itself (`REFLEX_AGENT`) gets a grant while the page
still shows "stopped":

```
$ curl ... -d '{"agent":"agent-old",...}'  /api/request           # becomes known
$ curl ... -d '{"token":"rt-operator-token"}' /api/stop-all        # stopped 1 agents: ['agent-old']
$ curl ... -d '{"agent":"agent-old",...}'  /api/request            # granted=False blocked=1
$ curl ... -d '{"agent":"agent-NEW",...}'   /api/request  x4        # tick 4 -> granted=True, blocked=0
state after: [('agent-NEW','FREE'), ('agent-old','blocked')]
```

The renamer got a real grant, four ticks after the person pressed stop.

**The contrast that points at the fix.** A *condition-based* halt already catches a renamer,
because the shared halt circuit is evaluated for every agent regardless of when it was first
seen. Install a dead-man's-switch halt and a brand-new name is caught with no per-name write:

```
$ curl ... -d '{"token":...,"class":"halt","heartbeat_ticks":2,"forbid_when_blocked":true}' /api/policy
$ curl ... -d '{"agent":"fresh-renamer",...}' /api/request  x4
tick 1: granted=False  why=['commitment: 0 of 4 consecutive intent ticks']
tick 2: granted=False  why=['halted (shared halt circuit): halted: 2 ticks without a heartbeat']
tick 3: granted=False  why=['halted (shared halt circuit): halted until a confirm lifts it']
```

**My answer.** The stop button should stop a *condition*, not a *list of names*. Add a global
"operator stop" latch that the shared halt circuit reads for **every** agent, known or not:
`stop-all` sets it, `resume-all` clears it (it already resets the halt state, so this is one
more field on the same operator-gated path). New and renamed agents then default to halted
until an explicit resume — which is precisely what a panic button should mean. Keep the
per-name `blocked` bit for targeted, surgical blocks; it is the global button that should not
be name-scoped.

**What it costs.** A legitimate new session started *during* a stop is refused until resume.
That is the correct trade for a "stop everything" gesture (fail safe, and the person is
already at the console), but it is a behaviour change and it will surprise someone who
starts a fresh agent mid-incident and finds it dead. The existing test that asserts "an
agent first seen after the press is not blocked" would flip to assert the opposite.

The heavier alternative is the one the docs already recommend — `REFLEX_REQUIRE_AGENT_TOKEN=1`
plus pre-bound names — under which an unknown/renamed name is refused outright. That closes
it too, but only if every name a person cares about is bound in advance, and it turns every
new session into an outage rather than a controlled stop. I would ship the global latch as
the default behaviour of the button *and* keep strict mode for the deployments that want
names nailed down.

## What I tried that did not break (the valuable half)

* **`/api/resume-all` lifting a halt that should have stayed.** No non-operator path reaches
  the shared-halt reset: every place that resets halt state (`_switch` on policy
  install/remove, `stop_all` on resume) is behind the operator token, verified by grep and
  by the endpoint refusing a tokenless resume (`HTTP=403`, "stopping and resuming every agent
  is the operator's"). And it cannot *durably* lift a condition-based halt: after a resume,
  the next tick re-evaluates the halt circuit, and with the heartbeat still absent the agent
  re-halts on tick 2 (shown above). What resume-all does is exactly what it says — the person
  lifting everything — and only the person can. The one honest note is blast radius: resume
  resets the halt class for *all* known agents at once, including any breaker/counter in the
  halt circuit, so there is no "resume this one agent's halt" short of `blocked:0` per name.

* **Making the device token out-reach the cable.** The Wi-Fi device is strictly weaker. It
  cannot unblock, cannot hold the heartbeat open, and cannot press stop/resume — each refused
  with a paired, valid device token:
  ```
  blocked:0  -> 403 "a block is lifted on the console or over USB, not over the network"
  heartbeat:1-> 403 "the heartbeat is this device's presence, which the console keeps itself"
  resume-all -> 403 "stopping and resuming every agent is the operator's"
  ```
  The cable (`cardputer_relay.Relay._key`) can do all three; the device (`device_tool`)
  cannot. A device can only `confirm`/`confirm_b` a call whose two-digit code and exact
  `reason` it can read off its own screen, or `blocked:1` an agent that has a live code —
  both stricter, both the person's to make. I could not get it to do anything the cable
  could not.

* **Writing a person's bit by dodging the hook guard.** Every path around the pattern check
  (IP alias, non-default port) still hits the operator-token wall at the console (F3). No
  `confirm` was written by any route I found that does not already hold the token.

* **The token in a log / history / Referer / screenshot** (the specific things asked). The
  fragment delivery is clean: the token is in the URL fragment, never sent to the server, so
  it is in no request log; `history.replaceState` clears the address bar; browsers strip the
  fragment from `Referer`; and the page makes no cross-origin request that could carry it.
  The exposure is not there — it is the header retransmission (F1) and the permanent
  `localStorage` copy, not the pairing link.

## 中文摘要

今晚改动我逐条打了，**边界的电路逻辑一处没破**：没写进任何 confirm、没伪造任何 grant、
Wi-Fi 设备顶不过网线、没有非操作者路径能解一个该留住的 halt。真正破的是**新 LAN 姿态下
对密钥的处理**。

- **F1（已证实·高，仅 LAN 姿态）**：页面 `refresh()` 每 2 秒轮询 `/api/state` 都把操作者
  令牌放进 `x-reflex-token` 头，明文过 Wi-Fi（无 TLS）。配对说明里"只过一次网"是假的——
  它一直在网上。同网被动监听者抓到令牌就等于拿到人的唯一密钥，能写 confirm、装规则、按
  停止/恢复。令牌还永久存在手机 `localStorage` 里，无过期。修：先把 `c3s_cli/cli.py` 的
  假注解改对；结构修法是给配对手机一个只读的设备令牌（Cardputer 那套机制现成），读路径用它，
  操作者令牌永不上网读。
- **F2（已证实·中）**：`_reader_may_look` 让**任何已绑定 agent 的令牌**在 LAN 上读到整个
  `/api/state`——别的 agent 的 pending `reason`、流水、全部 armed 位。`ISOLATION.md` 正是靠
  "读不到 reason"来论证容器花不掉别人的 confirm。修：agent 身份的 LAN 读只回它自己那几行。
- **F3（已证实·低，仅纵深防御）**：钩子自保护的进程杀死判据写死 `:8765`、host 只认字面拼写，
  于是 `pkill -f 8774`、`curl http://127.1:8774/...`、十进制 IP 都能绕过。但令牌兜底仍在
  （绕过去写 confirm 照样 403），杀掉后台钩子 fail-closed，属自我 DoS。修：端口从 CONSOLE
  取、host 拼写归一化。
- **大红按钮改名逃逸（用户要拍板的设计题）**：已证实。stop-all 只 block 按下时已知的名字，
  改名后第 4 拍就拿到 grant，而页面还显示"已停"。对照：**基于条件的 halt**（心跳死人开关）
  因为对每个 agent 都跑，能抓住新名字。**我的答案**：大红按钮应停"一个条件"而非"一串名字"
  ——加一个全局 operator-stop 闩，共享 halt 电路对每个 agent（含未知/改名）都读它，stop-all
  置位、resume-all 清零（本就走操作者令牌、本就重置 halt 状态，多一个字段而已）。代价：停止
  期间新起的会话默认被拒到 resume，这对"全停"手势是对的，但是行为改变、会吓到中途开新 agent
  的人。更重的替代是文档已推荐的 `REFLEX_REQUIRE_AGENT_TOKEN=1`+预绑名。建议全局闩做默认、
  严格模式给要钉死名字的部署。
